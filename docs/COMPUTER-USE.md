# 电脑操作（Computer Use）：设计与接力

> 让 Flowship 里的 AI 操作这台电脑上的**任何应用**（截图 / 点击 / 输入 / 打开应用）。用户不在电脑前时也能用（飞书里一句话遥控），**包括电脑已经锁屏之后**。macOS + Windows。
> 总开关「电脑操作」默认关；「锁屏时也能用」默认关；每一步都有用户看得见的开关、遮罩和审计。
>
> 这份文档讲「它是怎么搭的、哪些规矩不能破、改了怎么验证、哪些地方还没验证过」。给 Windows 同事做真机验收的步骤单在 `docs/windows-unlock-live-test.md`。

## 3. 会话与安全不变量

这些都由单测逐条钉死（改动前先读 `electron-app/desktop/session.mjs`、`manager.mjs` 的文件头，以及 `tests/desktop-session.test.ts`、`tests/desktop-manager.test.ts`）：

- **默认拒绝**：总开关没开 / 来源不被允许 / 没凭据 / 不支持 / 冷却中，一律不碰锁屏界面。总开关关着时只有 `desktop_status` 可用（只读，让 AI 知道为什么用不了），其余请求都是 `ACCESS_DISABLED`。
- **权限预检在解锁之前**：没权限就别去解锁一次。
- **读不到「是不是锁屏」= 不知道，不放行**：驱动的 `isScreenLocked()` 返回 `null` 时，会话开始、以及前台档每个动作之前的闸门都抛 `INTERNAL`（文案叮嘱 AI 告诉用户稍后再试、反复出现就导出诊断反馈），不往下走——把「不知道」当成「没锁」，macOS 上键鼠注入会直接落进可能正锁着的锁屏界面的密码框。这和解锁器对 `null` 的口径一致（「为安全起见不介入」）。前台动作闸门读到 `null` 只拒这一下、**不结束会话**（下一次再读，读到「没锁」就照常继续，一直读不到靠空闲看门狗收掉）；后台档的闸门读到 `null` 则不动它（后台档的前提就是锁着，只有明确读到「已解锁」才结束）。注意它和 §5.3「解锁器」里的另一条口径**方向相反但并不矛盾**：那条说的是「组件已经报告解锁成功之后」驱动读不到状态按成功算——密码已经输进去了，这时报失败会让一台已经解开的电脑没人收尾；这里说的是「还没动手之前」，不知道就别动。
- **一次错误即停**：自动解锁失败后进入 10 分钟冷却，期间不再尝试。输错开机密码会触发账户锁定，比「没解开」严重得多。只要**密码确实输进去过**就算「试过一次」：包括解锁过程中被取消、但取消来得太晚（密码已经输进去、却没解开）的情况——这种也进冷却并推 `unlock_failed`，不再静默取消；解锁器没声明 `attempted` 一律按「输过了」算。没输进去的失败（没权限 / 没锁屏 / 读不到密码 / 屏幕上是 UAC）不进冷却。**冷却在输密码之前预写**（第三轮评审）：`unlock()` 一调用就先把整段冷却写进内存 + 盘（`armUnlockCooldown`，按「这次会输错」落盘），结果出来后再结算（`settleUnlockCooldown`）——输过却没解开（含解锁器抛异常 / 没声明 `attempted`）→ 保持并从此刻刷新起点，解开了 / 根本没输过（`attempted:false`）→ 撤销。以前冷却要等 `unlock()` 返回之后才落盘，而输密码到返回之间最长十来秒（输入 + 等验证 + 取消观察），这段窗口里应用退出 / 崩溃 / 自动更新重启，重启后冷却是空的，下一次请求把同一个（可能是错的）密码再输一遍（`destroy` 是同步的、只 abort 就返回，没有机会补写）。预写期间设置页状态不报冷却（`cooldownProvisional`），免得 AI 正常解锁的十来秒里闪一下「解锁失败、冷却中」。**冷却截止时刻落盘**（会话层，macOS / Windows 共用：`cooldown-store.mjs` → `<userData>/desktop-state/unlock-cooldown.json`，文件 0600 / 目录 0700，只存一个时间戳，写入走「临时文件 + rename」）：输错之后重启 / 崩溃重启 / 自动更新 relaunch 不会把冷却清零——只放内存的话，下一次请求会把同一个错密码再输一遍。读不了或读不懂记录（被占用 / 写坏了）按**一整段冷却**算（fail-closed）；记录里的截止时刻最多只认「现在起一整段冷却」那么远，所以时钟被拨回去、文件被改成很远的未来都不会让功能永久不可用；写不进去的后果取决于是哪一步（第五轮评审：以前这里一句「内存里的冷却照样生效」只对其中一步成立，和上面「预写失败就拒绝解锁」自相矛盾）：**输密码之前的预写**没落盘 → 冷却回滚、这次不解锁（一个键都不输）；**输错之后**的结算没落盘 → 只记日志；内存里仍然生效，盘上留着的是输密码之前预写的那一段（起点比这次失败早十几秒），所以重启后冷却**仍在**、只是会早结束一点，不是「会丢」（第六轮评审 P3：旧文字和旧默认日志都写「重启后会丢」，是错的）；**撤销 / 重置**（解开了 / 根本没输过 / 用户重新保存了密码）时要把盘上改写成 0、却没写成 → 内存里已经解除、盘上还留着旧的那一段，重启后会多出一次冷却（方向是 fail-closed）。`persistCooldown` 现在由各步骤传入自己的日志文案，不再一律说「内存里仍然生效」；**只有输密码之前的预写会用它的返回值**（失败就拒绝解锁），结算 / 撤销 / 重置不看返回值、只记日志（没有兜底删除——`cooldown-store` 刻意没有删除接口，要加得先改它顶部「不删文件」的设计说明；第十八轮已定：不加）。冷却的**唯一人工出口**是用户在设置页重新保存开机密码（`manager.setCredential` 成功后清；Windows 上卸载解锁组件也清），没有任何绕过它的开关。Windows 解锁组件自己另有一份落盘的冷却（`state.txt`，§5.3），两份各自独立生效。
- **用户优先**：解锁前 3 秒内键鼠动过 = 用户在场，不介入；会话中检测到真实输入立刻结束并让位，用户停手满 30 秒前不抢回。
- **看门狗**：会话硬上限 15 分钟、无任何动作 3 分钟自动结束（AI 想继续要重新开始，会再走一遍完整流程）；遮罩一定会撤；结束时电脑锁回去（仅限我们解的锁，用户接管时不锁）。前台档每个 tick 还查两件事（读不到 = `null` 一律不算数、不结束）：**电脑被锁屏了**（屏保 / 用户手动锁 / 合盖睡眠，读到明确的「已锁定」）→ 以 `relocked_externally` 结束且不再锁、不再抢；**遮罩盖不全** → 以 `overlay_incomplete` 结束并锁回去（见下面「遮罩跟着显示器变化」）。顺序：用户接管 > 被锁屏 > 遮罩盖不全。
- **同一时刻只有一个任务持有会话**；开始 / 结束并发调用互不踩踏，解锁过程中被取消会等它停手，刚解开的会锁回去。**取消的观察窗口要罩住整段验证时间**：macOS 解锁器回车之后最多等 8 秒（`verifyTimeoutMs`）看是否解开，慢机器 / FileVault 下解锁要好几秒；取消时若已提交过回车，它会等到「取消时刻起 `cancelGraceMs`（2 秒）」和「回车时刻起 `verifyTimeoutMs`」两者中更晚的那个，才判「到底解开没有」——只给取消起 2 秒的话，取消恰好落在这段里就会被判「还锁着」，上层以为没解开、电脑却在稍后解开了，没人锁回去。
- **收尾分三段，第三段一定会跑**（`doEnd` 的 try/finally）：① 让进行中的开始 / 升级 / 注入动作停手；② 我们解锁的、该锁回去的就锁回去并确认；③ **不管前面怎么了**：撤遮罩、释放防睡眠、状态复位、发事件。以前没有 finally：阶段二里 `isScreenLocked()` 一抛，整个收尾带着异常出去——「要锁回去」的债丢了、遮罩没撤、没有任何事件，连「没锁回去」的本机通知都不会弹。
- **收尾期间飞着的只读动作，结果不交给 AI**：`runRead`（截图 / 列应用）读完后若会话已经结束 / 在收尾 / 换了一代，抛 `SESSION_EXPIRED`，这次读到的内容作废。否则用户已经说「停」之后，收尾窗口（等动作停手 + 两次锁屏等待，最长几秒）里飞着的截图照样返回，AI 仍拿到屏幕画面。
- **前台会话期间不让显示器睡眠**：睡了会锁屏（会话被 `relocked_externally` 打断），之后的截图是黑的。`session.mjs` 的 `keepAwake` 由 `index.mjs` 用 Electron 的 `powerSaveBlocker`（`prevent-display-sleep`）实现；只在前台档 active 期间持有（锁屏后台档本来就锁着），收尾 / 退出 / 出错的每条路都释放（`dropAwake` 幂等）；拿不到 / 放不掉只记日志，不影响会话。
- **所有请求串行**：键鼠注入不能交错；排队中的请求被取消后不再执行。
- **结束先等在飞的注入动作停手**（上限 3 秒），再锁屏 / 撤遮罩：否则长文本剩下的字和回车会打进锁屏界面的密码框，等于一次错误登录。
- **打字 / 回车不会落进锁屏界面**（第三轮评审）：`guard` 只在动作开始时看一眼锁屏，而 `desktop_type` 要打约 2 秒再加 80ms 才轮到 `submit` 的回车——这期间电脑被锁屏（热角、手动锁、屏保），余下的字加回车会落进锁屏密码框，等于一次错误登录，而且不进冷却。三道防线：① 看门狗每个 tick 读锁屏状态，读到明确的「已锁定」就结束会话（`relocked_externally`），会话一结束驱动的输入循环在下一批就看 `shouldStop` 收手；② 回车之前再过一遍会话闸门（`ctx.guard()`：锁屏 / UAC / 读不到锁屏状态都抛，动作作废，字可能已经打了一部分）；③ 会话已经在收尾时回车本来就不按。
- **收尾时被丢下的「僵尸动作」碰不到新会话**（第三轮评审）：收尾等在飞动作停手有上限（`actionDrainMs`），超时了照常收尾，卡住的动作稍后才返回——那时新会话可能已经 active，会话级的 `shouldStop` 是「没事」，僵尸动作就会接着把剩下的字打进新会话（可能是别的任务、刚解开的电脑）。现在每个动作绑一个会话世代（`actionEpoch`）：收尾不管等没等到都把世代 +1、在飞计数清零（`abandonInFlightActions`）；动作自己的 `shouldStop` = 会话不在 active **或**世代变了；世代变了的动作返回时不再碰新会话的计数 / 「最后注入时刻」（否则新会话的用户接管检测会因 `acting` 永远清不回 0 而失效）。
- **解锁进行中退出**（第三轮评审）：应用退出（`destroy`）时若正在解锁（输密码 / 等验证），`unlock()` 的结果没人等了，电脑可能马上（甚至已经）被解开，而此刻 `unlockedByUs` 还是 false——不锁回去，电脑就被留在「已解锁、没遮罩、人不在」的状态。现在 `destroy` 先记下「是不是正在解锁」：读得出仍锁着（`true`）就不用动，解开了 / 读不到就一并发出锁屏命令（宁可多锁一次）。
- **锁回去要「确认真的锁上了」才算数**：默认方式没锁上就用快捷键兜底再试一次，两次都不成功才报 `relock_failed`。
- **解锁成功后遮罩盖不上**：立刻锁回去并中止，绝不留下「已解锁、没遮罩、人不在」。
- **遮罩跟着显示器变化走**：遮罩窗口是按创建时那一刻的显示器范围定的，分辨率 / 缩放 / 旋转 / 摆放位置一变就会露出没盖住的缝。`overlay.mjs` 监听 `display-metrics-changed`，对应显示器的窗口立刻 `setBounds` 贴合（调不动就重建；这块显示器上本来没窗口、但显示器还在，就补建）。拔掉显示器之后才到的迟到事件不会给不存在的屏幕建出一个没人销毁的窗口。**遮罩盖不全 = 结束会话并锁回去**（第三轮评审「overlay 补建失败」）：会话中途接入新显示器 / 改分辨率之后，那块屏幕的窗口建不出来，以前只记一行日志——旁人看得见 AI 在干什么、而用户不在场。现在 `overlay.isComplete()` 把「有明确缺口」（某块显示器建窗口失败 / 窗口已被销毁）交出去，会话看门狗在**前台档 + 我们解锁的会话**里读到 `false` 就以 `overlay_incomplete` 结束并锁回去（与「解锁后遮罩盖不上就锁回去」同一个失败即关闭的口径；飞书侧不单独推这条，锁回去失败由既有的 `relock_failed` 推）。下一次 `desktop_*` 会重新开始、重新盖遮罩，还盖不上就在开始阶段报「遮罩没能显示」。遮罩实现没有这个方法 / 探测本身抛了 = 「不知道」，不为一次读不到结束会话；用户接管优先于它。**只用假 `screen` 验证过，没在真实改分辨率 / 多显示器的电脑上验证。**
- **截图拿画面有上限**：`desktopCapturer.getSources` 偶尔会挂住不返回，而桌面请求是一条串行队列——一个挂住的截图会让后面所有请求排着等，直到重启 Flowship（server 侧每个请求各自的 90 秒超时只让那一次工具调用失败，队列本身不松）。`screenshot.mjs` 给它设了 12 秒上限（`GET_SOURCES_TIMEOUT_MS`），超时就按截图失败抛错，队列继续走。
- **退出收尾要覆盖 `app.exit()` 路径**：Electron 的 `app.exit()` **不**触发 `before-quit` / `will-quit`，而「撤遮罩 + 我们解的锁就锁回去」不能只挂在 `will-quit` 上（否则用户不在场时，一次套用暂存更新的退出会留下一台既没遮罩也没锁屏的电脑）。`main.js` 的 `destroyDesktop()`（可重复调用、出错只记日志）在 `will-quit` 里调一次，每条以 `app.exit()` 收尾的路径（立即更新的 relaunch、退出时套用暂存更新）在「退出已经确定」之后、`exit` 之前自己再调一次；退出还可能取消的位置**不要**调（`destroy` 会摘掉设置页用的 IPC）。`tests/electron-browser-wiring.test.ts` 钉着这几处位置，并对账 `app.exit(` 恰好这两处——再加一条退出路径时它会红，提醒你也配上。

- **开机密码不能借错误文字漏出去**（`electron-app/desktop/redact-secret.mjs`）：密码「在手上」的地方只有 macOS 解锁器的 `unlock`（凭据 / 键入两步）、`checkCredential`、`setCredential`，钥匙串的 `set`，以及 `manager.setCredential`。这些地方下面是原生层 / 系统接口，它们抛的错误文字可能回显入参，而 `result.error` 会一路被 session / manager 原样放进 `DesktopError` 的消息、`unlock_failed` 事件、审计和日志。所以**在握着密码的那一层就地抹掉**（`redactSecret` / `redactError`：整串密码替换成 `•••`；抹在 `.slice(0, 160)` 截断**之前**，否则被截断的半截密码就认不出来了）；`manager.setCredential` 另有一道兜底（解锁器自己也抹）。**「整串」不只原样那一种**（第三轮评审：只做精确子串匹配时，密码含 `"` 或 `\` 的话，原生层 / 管道把入参 JSON 序列化后回显的那份就漏了）：同一个密码在 JSON 字符串里的样子（`"` → `\"`、`\` → `\\`、控制字符 → `\uXXXX`）、`encodeURIComponent`、反斜杠转义引号（`'` → `\'`、`"` → `\"`、`\` → `\\`：shell / JS 字面量 / `util.inspect` 一类的回显）也一并抹，长的写法先抹以免留下半截；有意不盖：base64 / hex / 二次编码（驱动与原生层不会这样回显一个键盘输入的字符串）、只回显了其中几个字符的。**密码长度也不借耗时漏出去**：输密码那一步（macOS 的 `type`、Windows 的 `unlock`）的步骤耗时一律报 `0`——耗时随密码长度线性增长，而步骤事件会进审计 / 设置页测试结果 / 导出的诊断包。单测用「会把密码回显进错误文字的毒化原生层」做端到端断言（`desktop-unlocker-darwin` / `desktop-keychain-darwin` / `desktop-manager` 里用真 darwin 解锁器的用例；「所有可能带密码出门的地方」那张清单里第三轮补上了**导出的诊断文件**——用户会把它发给别人排查问题，它却曾不在清单里，现在真导出一份、把写出去的路径和内容一并查，并有自检用例证明清单抓得出塞进去的密码），并做过变异验证（拿掉生产侧的抹除，断言必须变红——以前这几条泄漏断言是恒真的，因为喂给被测代码的错误文字里根本没有密码）。Windows 一侧密码只在 `set` 请求里交给组件，管道通信出错时 Node 侧只给错误类型、不回显原文（§5.3）。
- **设置页开关显示的是主进程的真实状态，不是草稿**（`computer-use-card.tsx`）：两个总开关的显示优先级 = 进行中的写（写完后留 10 秒宽限，免得刷新回来前闪回旧值）> 主进程报告的真实状态（`status.enabled` / `lockedAccessEnabled`，仅 `supported:true` 时采信）> 草稿。以前直接读草稿：写失败 / 被拒后开关仍显示「已开」而主进程其实没开，用户以为功能开着；这张卡自己弹的失败 toast 以前一概写「会自动重试」，对服务端 4xx 拒绝 / 配置没加载成功是假话（这两种不重试）；现在由 `saveFieldValue` 自己弹「保存失败」，并按情形说清楚会不会自动重试（只有 5xx / 网络错误 / 408 / 425 / 429 才重试（其余 4xx 这条路径——以前这里写的「没有重试这回事」是错的，下面「补清」的等待窗口说的重试才是真的）。主进程装配失败（`initError`）或平台不支持时，总开关**只能关、不能再开**，「锁屏时也能用」行只在它显示为开时才出一行精简版，让已经开着的用户至少能把它关掉。所有写流程都不会 reject（`settleWrite` / `safeRefresh` / `writeVia`）；「保存开机密码」对话框的 `handleSave` 整段在 try/catch 里（`await writeLockedAccess(true)` 以前在 try 外，抛了会让 `saving` 永远为真、按钮永远转圈），失败 toast 里的密码用 `scrubSecret` 兜底抹成 `•••`。**装配失败时也能清开机密码**（第三轮评审；以前「清除」通道在装配失败时直接 reject，一份能自动解锁电脑的密码只能等功能恢复才删得掉）：`index.mjs` 的 `clearCredentialDegraded`——`manager` 没建起来时「清除」不走 `requireManager()`，改用一个空壳驱动建出解锁器（钥匙串 / 解锁组件客户端本来就不用驱动）、只调它的 `clearCredential()`；永不抛、返回 `{ ok, error? }`，解锁器也建不出来（钥匙串零件抛错）时如实说原因、不假装清掉了；**不记审计**（审计日志本身也是装配的一部分、可能没建起来），只写应用日志。卡上这时多一行「已保存的开机密码」+「清除」（读不出有没有存过，所以不说「已保存 / 未保存」，没存过时清除也算成功）。关掉「锁屏时也能用」本身仍**不会**连带清密码（那一行的提示文案如实写了这一点，并指向这个清除入口）；没有桌面驱动的平台（Linux 等）没有这回事、不显示。**关开关没写进去时**（第三轮评审）：设置页对 5xx / 网络错误会自动重试，重试成功时开关是在没人经手的情况下关掉的、密码没人清——`disableLockedAccessFlow` 在「开关没写进去、钥匙串里有密码」时登记一个「补清」意图，等主进程**确认**锁屏开关真的关了（`actualLocked === false`，不看会乐观更新的草稿）、草稿也是关、钥匙串里还有密码，才补清（`deferredClearVerdict`：用户又把开关打开了 / 密码已经没了 → 作废；主进程还没确认 → 继续等）；这里是界面层的补救，不是主进程的「开关一关自动删密码」，判断见 HANDOFF。**写开关失败只收起自己登记的那份暂存**（`writeVia` + `useSwitchPending`）：以前一次失败的写会把用户随后又点的那一下的暂存也清掉，开关闪回旧值。**主进程返回的状态要过运行时校验**（`isComputerUseStatus`）：界面与主进程版本不一致时，畸形快照不能渲染（卡片里 `status.permissions[...]` 之类的解引用会让整张卡崩掉）——校验不过 = 一次读失败，连续两次才显示「主进程返回的状态格式不对（界面和主进程的版本可能不一致）」，`adopt` 也不采信畸形快照。失败原因统一走 `readableErrorText`（去掉 Electron IPC 的 `Error invoking remote method '…'` 前缀、折叠空白、限长；带密码的调用先抹再截断）。**无障碍**：四个开关都有 `aria-label`（总开关「电脑操作」、三处「锁屏时也能用」），会动的提示文字（警告 / 开关与主进程不一致的说明 / 打不开的原因 / 状态读不出来）是 `role="status"`，「保存开机密码」输入框带 `aria-label="开机密码"` 与 `autoComplete="new-password"`（不让浏览器 / 密码管理器把它当成登录框去填别的密码）。**第四轮评审又补了四处**：① **「已存好但冷却没清掉」**（Windows，主进程回 `{ ok:false, saved:true, error }`）：`saveCredentialFlow` 按「已保存」处理——照样写开关、对话框关掉（不留着让用户再输一遍）、刷新状态，并用 `toast.warning(error, { duration: 10_000 })` 展示主进程那句话（`error` 为空有兜底文案，且过 `scrubSecret`）；只认严格的 `saved === true`；② **补清不能碾过用户的新动作**：关开关写盘慢（或失败后等自动重试，退避 2 / 8 / 30 秒，最长约 40 秒）期间，用户可能又点开、或存了新密码——`disableLockedAccessFlow` 的 `shouldClear` 守卫 + `ComputerUseView` 里的 `lockedSeqRef` 序号（点关、点开、存密码各 +1，补清意图记着登记时的序号，真动手清之前比一次）；取舍：存密码一开始就把补清意图作废，所以**保存失败时这条意图丢了、密码会残留**（用户可手动「清除」；手动清除没加序号）；`clearCredential` 的 IPC 一旦发出就撤不回，约百毫秒的窗口；③ **`Switch` 的禁用样式**：Base UI 的 Switch 渲染成 `span`，Tailwind 的 `disabled:`（`:disabled` 伪类）对它不生效，改成 `data-disabled:`（`tests/ui-switch-disabled.test.ts` 用 SSR 钉住根节点是 span、没有 `disabled` 属性）；同类的 `checkbox.tsx:56` 裸 `disabled:`（SSR 实测 Base UI 的 Checkbox 也是 span）与 `switch.tsx` 里条件调用 `useFormDisabled()` 只汇报、**没改**；④ **「保存开机密码」对话框加 `disablePointerDismissal`**：里面是输了一半的开机密码，点一下遮罩就整个丢掉太伤；Esc 和「取消」仍能关（卡片里另一类 `confirm` 基于 AlertDialog，本来就不能点遮罩关）。评审还提了 `res.error` 三处直出：核对后三处都有兜底，保存路径已脱敏、另两处入参里没有密码、主进程已限长，再加一层 UI 限长属于加固，没改。**以上这些（禁用样式、点遮罩不关、10 秒警告）都没在真实窗口里看过**，只有 SSR 与纯函数测试。
- **后台档的输入类动作不能偷偷升级成解锁**：只有 `desktop_screenshot` / `desktop_apps` 带 `foreground:true` 才会走解锁。设置页的两个测试按钮（见 §5.2）期间都不接 AI 的桌面请求。

## 4. macOS（概述）

- 驱动 = koffi 调系统 API；权限：**辅助功能 + 屏幕录制**（`permissions.mjs`）。没有辅助功能权限就**不输入**（系统会静默丢弃事件，等于白输一次密码）。
- 开机密码放在 Flowship 自己的**专用钥匙串文件**里（`<userData>/desktop-keychain/unlock.keychain-db`；条目名见 `index.mjs` 的 `keychainNames`，test 实例与正式实例分开），**不放登录钥匙串**。原因（实测，完整推导在 `credentials/darwin-keychain.mjs` 文件头）：登录钥匙串里的条目带一份「分区列表」，自签证书下它记的是创建者那一版的代码哈希，每次升级都读不出旧版存的条目，用户每升级一次就得重输开机密码；另外锁屏 / 睡眠后登录钥匙串也可能读不出来。
- **诚实的边界**（对外文案别说得比这更满）：专用钥匙串要能无人值守地解锁，它的口令只能用「本机硬件标识」派生，**不是秘密**。真正的防线是条目的访问控制（读它要有 Flowship 的签名身份），不是文件加密：拿到文件却不在这台电脑上的人打不开；这台电脑上的其它程序走系统接口读会被拒；但能以 Flowship 身份运行代码的程序、或自己解析文件又知道口令派生方式的程序读得到。「升级不用重存」只对**固定证书**签名的包成立，ad-hoc 签名每个版本身份都不同，照旧要重存。
- 解锁 = 唤醒 → 确认确实是锁屏 → 从钥匙串取密码 → **真实键码**输入 → 回车 → 确认已解开；**只试一次**，输入前再确认一次仍是锁屏。返回值里的 `attempted` 告诉上层「密码是不是真的输进去过」：没输过的失败（没权限 / 没锁屏 / 读不到密码 / 密码里有键码模式输不了的字符）不触发冷却。锁屏支持 `method:"shortcut"`：默认方式没生效时 session 换成锁屏快捷键再试一次。取消时的观察窗口、读不到锁屏状态、冷却落盘、收尾 try/finally、防显示器睡眠、错误文字里抹密码，规矩都在 §3。逻辑与测试：`unlockers/darwin.mjs`、`tests/desktop-unlocker-darwin.test.ts`、`tests/desktop-keychain-darwin.test.ts`。**输密码这一步的耗时不上报**（`ms: 0`，第三轮评审）：输入循环的耗时随密码长度线性增长，而步骤耗时会原样进审计文件 / 设置页测试结果 / 导出的诊断包，报出去等于把开机密码的长度送了出去；唤醒 / 验证这些与密码无关的步骤照常报。
- **`desktop_open_app` 的绝对路径只认「应用程序」目录里的顶层 `.app`**（第三轮评审）：以前任何位置的 `.app` 都能被一条路径跑起来——下载目录 / 桌面 / 临时目录 / U 盘 / 应用包里面的辅助程序，都可能是刚下载或刚放进去的任意程序，而模型可能被屏幕上的内容带偏。现在要求路径以 `.app` 结尾，且在 `/Applications`、`/System/Applications`、`/System/Library/CoreServices`、`~/Applications` 之下（和「按显示名找」认的同一批目录），不含 `.app/`（不进应用包里面）；先按 POSIX 规则规范化（`..` / `.` / 重复斜杠）再判断、**打开的也是规范化后的那条路径**——验证的和执行的是同一个字符串。**符号链接没有解析**：白名单目录里本身就是个指向别处的符号链接 `.app` 会过关（要先能往那几个目录里放东西）；这条是白名单、不是沙箱。按应用名打开的路径不受这条影响（它本来就只在这几个目录里挑）。**Windows 没有目录白名单**（`rejectOpenTarget` 只拒网址 / UNC / 脚本 / 文档这些，见 `drivers/win32.mjs` 头注释）——没加的考虑：Windows 的应用散落在 `Program Files`、`AppData\Local`（不少应用只装在这里）和便携版的任意目录，白名单要么太松、要么会挡掉正常用法，又没有真机可验；这是与 macOS 不对称的有意取舍（判断题，不是遗漏），真机验证后再定。
- 遮罩：解锁后每块显示器盖一个全屏窗口（不抢焦点、鼠标穿透、最高层级、页面是静态内联 HTML）。**macOS 27.2 + Electron 42 实测：防截屏设置不管用，整个屏幕被截成一片纯黑**。所以 `capture-guard.mjs` 在运行时对照「带遮罩 / 撤了遮罩」两张截图，发现遮罩影响了画面，就在截图的一瞬间把遮罩变透明（截完立刻恢复，`overlay.mjs` 还有 5 秒超时兜底，屏幕不会一直裸着）。**取舍**：这种系统上每次截图旁人能在约半秒内瞥见真实桌面——这是在「AI 完全看不见屏幕」和「截图瞬间屏幕裸露」之间选的后者。守卫是平台无关的，Windows 上同样生效。
- **第四轮评审里「成立（或部分成立）但没修」的项**（如实记录，对外文案不要说得更满）：
  - ① **`desktop_type` 文字里自带的换行**（评审 A3-a 的另一半）：`desktop_key` 连按回车已改成每按一下之前过会话闸门，但 `desktop_type` 的文字里自带 `\n` 时，换行 = 回车键，仍只靠看门狗（0.3 秒读一次锁屏状态）加驱动每 12 个字符一批的 `shouldStop` 收手；窗口 ≈ 300ms + 一个批次，这段时间里电脑被锁屏，已经发出去的批里的换行会提交到锁屏界面。要收窄得让 `shouldStop` 自己去读锁屏、还要避开后台档，Windows 读锁屏的开销没法验证，所以没做（Windows 前台驱动的 `typeText` 每批发出前自己复查输入桌面，见 §6；macOS 驱动没有）。
  - ② **`destroy` 在「已回车、验证中」不锁屏**（A3-b）：会话在读到仍显示锁屏时不发锁屏命令（那时发是空操作）；根治要把 `main.js` 的退出路径改成异步等待，超出范围；无条件发命令还会推翻 `desktop-session.test.ts` 里一个现有用例。
  - ③ **macOS 解锁器回车前不复查锁屏**（A3-c，部分成立）：输入前有最后一次确认（`unlockers/darwin.mjs`），回车前没有（Windows 有 `StillLockedBeforeSubmit`）。补上要牵涉 `attempted`、冷却和文案；已经打出去的字符撤不回、还得告知用户，需要单独设计，只记录。
  - ④ **审计时间戳与密码长度弱相关**（A3-d）：输密码那一步的耗时已置 0，但 `audit.mjs` 里相邻记录的 `at` 差仍随输入耗时变化（`begin` 到 `unlocked` 的差同理）。局部抹平无法根除，粗化会损失排障价值，需要产品取舍。
  - ⑤ **拒绝路径上的 `unlocking` 事件没有对应的终态**：`unlocking` 在冷却预写之前就发出；预写没落盘（或先盖遮罩失败，这条本来就如此）抛错时，事件序列里有 `unlocking` 却没有 `unlocked` / `unlock_failed`。AI 会拿到带原因的错误转告用户；没动事件顺序（会牵动事件测试，收益低）。
  - ⑥ **`capture-guard`：exposed 模式下撤了遮罩、截图仍几乎全黑 / 全是遮罩色时，仍把这张图交给 AI**（评审 C4，设计取舍）：只写日志，不拒绝、不报错——屏幕可能本来就是黑的（深色壁纸 / 全屏黑色应用），拒绝会让 AI 在这种屏幕上彻底看不见；交出去的永远是撤了遮罩的那张、不是带遮罩的那张。代价：撤遮罩没生效时 AI 拿到的是黑图，分不清是「屏幕本来黑」还是「撤遮罩失败」；不会泄露任何内容。
  - ⑦ **pi 压缩摘要没脱敏**：`pi-session-persist.ts` 头注释已写明是已知缺口；摘要的输入本来就是落盘前脱敏过的，评审自己也不按 P1。

## 5. Windows

### 5.1 为什么锁屏时难

Windows 锁屏时，「输入桌面」从用户桌面（`Default`）切到 Winlogon 的安全桌面，只有 SYSTEM 身份的进程才能在上面输入。普通用户进程既注入不了键盘，也碰不到锁屏界面。但用户桌面上的进程**照常在跑**，窗口句柄照常有效。这催生了两条路线：

### 5.2 档 1：锁屏后台档（默认，不装任何东西）

电脑一直锁着，不解锁、没有遮罩、不碰密码。`drivers/win32-background.mjs`：

- 截图 = 枚举主屏上的可见顶层窗口 → 逐个 `PrintWindow(PW_RENDERFULLCONTENT)` → 按 Z 序叠成一张主屏大小的图（画不出来的窗口在结果里标出）；
- 点击 / 拖拽 / 滚轮 = 找到命中的最上层窗口和最深的子控件，`PostMessage` 鼠标消息；键盘 = `PostMessage` 到焦点控件；首次操作某窗口前补发 `WM_ACTIVATE` + `WM_SETFOCUS`。
- **`PrintWindow` 卡住的窗口**：对一个窗口的 `PrintWindow` 等 3 秒（`PRINT_TIMEOUT_MS`）没返回，这次截图把它标成 `timeout`，之后 60 秒（`HUNG_SKIP_MS`）内不再对它截图。**那次调用占着的 GDI 对象（内存 DC / 位图 / 选入的旧位图）不能立刻释放**：调用可能还在往里画，而 GDI 句柄值释放后会被系统重新分配给别的对象，晚到的绘制会写进不相干的东西。所以它们搁在 `stuckPrints` 里，等那次调用真的返回了（成功失败都算）由 `releaseWhenSettled` 释放；上一次还没返回的窗口，哪怕已经过了 60 秒也不叠加新的 `PrintWindow`（再发只会多泄漏一组 DC + 位图、多占一个 koffi 工作线程）。**真实 `PrintWindow` / koffi 异步调用在锁屏状态下的表现没在真 Windows 上验证过，只有假 ctx 的单测。**
- **一帧的内存预算**（第三轮评审）：合成之前每个窗口的整张位图（宽 × 高 × 4）都要留着，单个最多 4096×4096（约 64MB）、一帧最多 24 个窗口——最坏 1.5GB，会把主进程吃垮。现在窗口按 Z 序从上到下取，累计超过 `MAX_FRAME_BYTES`（256MB，`ctx.maxFrameBytes` 可覆盖，测试用）就停：更下面的窗口（多半已被盖住）在结果里记 `skipped`、不再 `PrintWindow`，让 AI 知道下面还有窗口没画。256MB 是拍的数（够几个全屏 4K 窗口叠着），真实机器上要量。
- **GDI 对象逐步释放**（第三轮评审）：每次 `PrintWindow` 要用一个内存 DC 加一张位图加「选入的旧位图」。以前收尾是两个裸调用——`DeleteObject` 一抛，`DeleteDC` 就被跳过、内存 DC 永远泄漏；「把旧位图选回去」抛了，位图还选在 DC 里就删不掉。现在正常路径与超时路径共用 `releaseGdi`：还原旧位图 / 删位图 / 删 DC 各自 try、一步出错不挡后面的，出错只记日志、不盖掉截图本身的结果；没选回去的会在收尾补选一次。
- **点在标题栏 / 菜单栏 / 边框上的点击与拖拽起点被拒**（第三轮评审）：后台档发的是客户区坐标的鼠标消息，非客户区不处理它——以前这类操作「成功返回、什么也没发生」，AI 会以为窗口已经最小化 / 关掉。现在没下钻到任何子控件、点又落在顶层窗口客户区原点的上方或左边，就抛 `NEED_FOREGROUND`（上层让 AI 升级到前台档，解锁不可用就如实告诉用户）。自绘标题栏的应用（Chromium / Qt / WinUI 无边框）标题栏本来就在客户区里，不在此列；**右 / 下边框读不到客户区大小，没有检查**；`WM_NC*` 消息在锁屏下是否可用没在真机上验证过，所以选择「拒绝」而不是「试着发」。

**不是万能的**：依赖 GPU / DirectComposition 的应用（Chromium、Electron 系：浏览器、飞书、VS Code）锁屏时被当成「被遮挡」，会停止渲染，可能截出旧画面或操作无效；管理员权限的窗口会被 UIPI 拦下。所以它只是「能用就省去解锁」，用不了时上层让 AI 升级到档 2。

设置页有两个测试按钮，测试期间都不接 AI 的桌面请求：

- 「测试后台操作」（`background-probe.mjs`）：会**真的锁屏**，用一个自己开的经典控制台窗口当靶子（不碰用户的任何应用），在锁屏下截图、打字、读窗口标题，一次点击回答「机制本身在这台电脑上通不通」，并列出哪些应用锁屏时画不出来（只列进程名和状态，不含标题）。电脑保持锁屏，用户自己解锁。
- 「测试锁屏可用」（Windows 上叫「测试自动解锁」，和后台测试区分开）：强制走解锁（前台档的整条链路：锁屏 → 自动解锁 → 遮罩 → 锁回去）。

### 5.3 档 2：解锁组件（可选，实验功能，默认不装）

后台档不够用时（某些应用锁屏时画不出界面）才用：装一个以 SYSTEM 身份运行的小服务 + 保存开机密码，AI 就能自动解锁、盖遮罩、干完活再锁回去。

**解锁器（`unlockers/win32.mjs`）里几条容易被「优化」坏的取舍**（都有单测）：

- 只试一次，绝不重试；`attempted` 如实告诉上层「密码是不是真的输进去过」：连管道都没连上的失败不算，其它（超时 / 回应中断）按「试过」处理。
- 请求发出之后**不能取消**：组件那头一旦开始输入，必须等它给出真实结果。取消时若已解开，以 `CANCELLED_AFTER_UNLOCK` 告诉上层去锁回来。
- 组件说「已解锁」之后，驱动只在**明确还显示锁屏**时才判失败；读不到状态（null）按成功算。组件是在系统桌面层面确认的，这时返回失败会让一台已经解开的电脑没人收尾，比误判成功更危险。
- `supported` 恒为 `true`：「装没装组件」由 `helperStatus` / `hasCredential` 表达。`supported:false` 会让设置页整块隐藏，用户就看不到安装入口了。
- 开机密码在 `setCredential` 时一次性交给组件，Flowship 这边读不回它。请求里带着密码，所以管道通信出错时只给错误类型、不回显原文。

#### 组件本体（一个 exe，三种模式）

- `service`：常驻（计划任务 `\Flowship\Flowship Unlock Helper`，SYSTEM，开机启动，崩溃后每分钟重启、最多 5 次）。命名管道服务端，**只接受安装时登记的那个 Windows 账户**；保存 / 删除开机密码（DPAPI 加密）；`check` = 确认已保存的密码读得出来、也打得出来（**不会**校验它对不对，组件没法知道）；记住解锁冷却（落盘）；需要解锁时拉起 typist。
  - **接受循环运行期永不因为「接不到客户端」而退出**（第二轮评审 #12）：管道最多 8 个实例（`MaxInstances=8`），每个连接最长占 90 秒（`ClientTimeoutMs`）。登记账户下的进程（ACE 允许它连、也允许它创建同名实例，见 §5.4 ②）可以把 8 个实例占满，这时下一次 `CreateServer()` 会抛。以前循环里连续失败 20 次就退出（退出码 7），而计划任务只在「崩溃后每分钟重启、最多 5 次」——同账户进程占着不放，服务退出 → 重启 → 再退出，5 次之后任务不再重启，解锁组件**永久停摆**。现在：**启动阶段**的失败（已有实例 3 / 读不到授权账户 4 / 多次建管道失败 5 / 写不了 `pipe.txt` 6）照旧退出（计划任务会重拉），**运行阶段**接不到客户端 / 建不出新实例一律不退出——先把刚连上的客户端交给工作线程（`connected = listening; listening = null; worker.Start()`），再去建下一个监听实例，这样实例被占满时已经连上的客户端照常被服务；监听实例坏了就丢掉重建；建不出来按 200 ms → 1 s 退避重试，日志只记开头几次、之后每 60 次一条，且**不记 `ex.Message`**。退出码 7 已从码表里去掉。后果：占着实例不放的同账户进程只能让组件**暂时连不上**（可用性，占用一释放就自己恢复），它读不到密码、也解不了锁。**这一块只经过静态对账 + Roslyn C# 5 编译检查（见 §6），没有在真实 Windows 上跑过**；真机验证见 `docs/windows-unlock-live-test.md`。
- `typist`：一次性。由 service 用 `CreateProcessAsUser` 在**控制台会话的 winlogon 桌面**上拉起：确认电脑确实锁着（判据见下）→ 读出保存的密码 → 唤醒锁屏（Shift 轻点 + 鼠标微动，等约 1.5 秒）→ 输入前**再按同一标准确认一次** → Caps Lock 开着就先按掉 → 逐键输入（键间隔 25ms）→ 回车 → 最多等 9 秒看输入桌面是否切回 `Default`。整个 typist 最长跑 40 秒，超时按「试过一次」处理（进冷却）。结果通过退出码告诉 service。密码只在这个进程内存里短暂存在，不进命令行 / 环境变量 / 日志。
  - **「确实锁着」的判据（只信正面证据）**：输入桌面是 `Default` ⇒ 没锁屏，一个键都不按（退出码 10 `NOT_LOCKED`）。不是 `Default` 时，锁屏和 UAC 等安全桌面都在 Winlogon 上、光看桌面名分不开，要再读**会话锁定标志**（`WTSSessionInfoEx` 的 `SessionFlags`）：明确是「已锁定」才输入；明确是「未锁定」且输入桌面是 Winlogon ⇒ UAC 之类（退出码 16 → `SECURE_DESKTOP`）；**读不出来 / 数据对不上预期 ⇒ 按「未知」处理（退出码 13 → `DESKTOP_ERROR`），也不输入**。「对不上预期」指结构 `Level` 不是 1，或结构里的会话号不等于本进程自己的会话号（偏移猜错了就会这样），以防把垃圾数据当成标志位。屏保这类「不是 Winlogon、会话也没锁」的桌面只在唤醒前放行（唤醒会把屏保关掉），输入前的最后一次确认一律拒绝。这几个退出码都落在 20 以下（没输过密码），service 回 `attempted=0`、不进冷却。
- `selftest`：安装时编译完跑一次（键位表完整、数据保护来回加解密正常、`INPUT` 结构大小对得上、系统 API 都解析得到），不碰任何真实凭据。它还会读一次**会话锁定标志**：读成「未知」就退出码 27（安装失败码 15）——这台电脑读不出会话是否锁定，装了也没法安全解锁，不如装的时候就说。

协议：命名管道，UTF-8，一行一条，LF 结尾。请求 `FS1<TAB>verb[<TAB>k=v]…`（value 百分号编码），响应 `FS1<TAB>ok|err<TAB>code=XXX[<TAB>k=v]…`。动词：`ping / status / set / clear / check / unlock`。结果码与文案在 `protocol.mjs` 的 `RESPONSE_CODES`。

**硬规矩**（写在 C# 文件头，单测逐条对账）：

1. 一次解锁**最多输入一次密码，绝不重试**。只要密码**确实输进去过**（响应里 `attempted=1`：没解开 / 输入中途失败 / 超时 / typist 异常退出，都按「试过一次」算），service 就记 **10 分钟**冷却（落盘，重启 service 也不清零），期间一律拒绝（`COOLDOWN`）。没输进去的失败（没锁屏、屏幕上是 UAC、读不到密码、有打不出的字符、拉起 typist 失败……）是 `attempted=0`，不进冷却。解锁成功、重新保存开机密码、清除开机密码都会清掉冷却。**冷却状态宁严勿松（fail-closed）**：截止时刻同时记在 service 的内存里和 `state.txt` 里，取两者中更晚的——状态文件写不进去 / 被删 / 被改，这次 service 运行期间冷却照样生效；文件在但内容读不懂（写了一半 / 被改过）按「文件最后修改时间起算一整段冷却」；文件在却读不了（被占用 / 没权限）**同样从最后修改时间起算**（修改时间是元数据，通常照样读得到；`Start` 只在失败的那一刻写一次，所以「修改时间 + 一整段」≈ 当时记下的截止时刻），连修改时间也拿不到才从「第一次发现读不了」的时刻起算（记在内存里、之后固定）——总之**会倒计时**（第三轮评审：以前读不了恒回一整段、每次都重新计，状态文件只要一直读不了冷却就永远不结束，重新保存密码也没用）；只有「文件不存在、内存里也没有」「记录的截止时刻已过」或「内容是 `Clear` 写的已清除标记 `0`」才算没有冷却。**「文件不存在」只认 `FileNotFoundException` / `DirectoryNotFoundException`**（第四轮评审）：以前先问 `File.Exists`，而它遇到「所在目录没权限」也返回 `false`（吞掉错误）——状态文件明明在，却被当成「没有冷却」（少冷却），`Clear()` 也会把「删不掉」当成「本来就没有」回 `true`（谎报）；现在 `Remaining` 直接读、`Clear` 直接删，其余异常一律走上面「读不了 / 删不掉」那几条路；`CredStore.Delete`（清除开机密码）同理（`DeleteIfPresent` 只吞「目录不存在」）。**读到的截止时刻比「现在 + 一整段」还远时（状态文件被改过 / 时钟被往回拨过）是「夹紧」、不是「封顶」**（第四轮评审）：第一次发现时定下「那一刻 + 一整段」并固定下来（`clampedUntilTicks`，只由 `Start()` / `Clear()` 重置；时钟回拨使「现在 + 一整段」变小时，固定值也会被压回去），之后照常倒计时、照常结束；以前是「超过一整段就回一整段」，每次读都回满格，冷却永远结束不了。**已知限制**（第五轮评审，没改）：夹紧值只由 `Start()` / `Clear()` 重置，所以同一个冷却期里发生两次时钟回拨时，第一次夹出来的固定值如果已经过期，第二次读到远未来的截止时刻会沿用这个过期的值、冷却立刻归零——方向是 fail-open；要连着两次改系统时钟（需要管理员权限）、中间还要熬过第一次那一整段，触发条件极窄。要补就得改「过期的夹紧值」怎么处理，那和上面「不能让冷却永远结束不了」「过期的旧夹紧值不能把新冷却当场判成已结束」两条取舍相冲，所以只记下来、没改，留给用户裁定。**组件版本因此升到 v2**（`Const.Version` / `Const.Proto` ⇄ `HELPER_VERSION` / `PROTOCOL_VERSION` 同时 +1；第三轮改了冷却恢复语义却没升版本，装着旧版的机器不会被设置页提示——这是第四轮评审的 P1-2）：旧版 service 没有这些行为，装着 v1 的机器要点一次「安装」升级。**`Clear()` 返回 bool**（第三轮评审）：删掉了 → `true`；删不掉就**改写成 `0` 标记**（读到 `0` = 没有冷却；光留着的话，下一次解锁请求照样被冷却挡住，而用户刚被告知「重新保存开机密码可以立即恢复」）→ `true`；连改写也不行 → `false`，冷却照旧生效到截止时刻（往安全的方向倒）。`DoSet`（保存开机密码）先存密码、再清冷却，**清不掉、而且冷却确实还在**时不回 `OK`，回 `COOLDOWN_NOT_CLEARED`（`saved=1` + `wait=还剩几秒`）：密码**已经存好了**，只是上一次失败的冷却没清掉；Node 侧把它翻成「开机密码已经保存好了，但上一次自动解锁失败留下的冷却记录没能清掉（…可能被安全软件占着）：冷却结束之前仍不会自动解锁，约 N 分钟后恢复；也可以稍后再点一次「保存」」（`describeSetFailure`，`N` 向上取整、至少 1），解锁器 / 设置页都不把它当成功（以前不管清没清掉一律回 `OK`，用户以为自动解锁已恢复、而下一次请求被冷却挡住）。**v3（第五轮评审）**：清不掉、但记录里的截止时刻**早已过了**（`Remaining()` 为 0，盘上只是个没人再看的过期时间戳）时，冷却其实并不存在——这种情况只记日志、照常回 `OK`；v2 一律回 `COOLDOWN_NOT_CLEARED`，对用户说「冷却记录没能清掉、约 N 分钟后恢复」，而 N 其实是 0，是误报。判断用的是 `Cooldown.StillBlockedSeconds()`（`Remaining()` 向上取整成秒；读不了状态文件时 `Remaining()` 按修改时间起算、不是 0，所以「读不了」仍按有冷却处理）。这个改动改的是 service 的运行行为，所以 `Const.Version` / `Const.Proto` 与 `HELPER_VERSION` / `PROTOCOL_VERSION` 同时升到 3（装着 v2 的机器要再点一次「安装」；v2→v3 的原地升级没在真机上走过）。清除开机密码（Node 侧 `unlockers/win32.mjs` 的 `clearCredential`、C# 侧的 `DoClear`）**故意没有版本闸**：Node 侧只看组件装了没有、在不在跑，不看版本；即使装着旧版组件、设置页正提示「点安装升级」，用户也必须能把自己保存的开机密码删掉（第五轮评审确认这是有意的；两处都写了注释）。「读不了 → 倒计时」「删不掉 → 改写标记」「改不了 → `false`」这几条是在 pwsh / .NET 里把真实的 `Cooldown` 类真跑过的（§6），不是只对账文本。
2. **没有「会话确实已锁定」的正面证据就一个键都不按**：输入桌面是 `Default`（没锁屏）不按；输入桌面是 Winlogon 但会话没锁定（UAC 权限确认等）不按——UAC 里回车默认是「是」，把密码连同回车打进去等于替用户点了同意；会话锁定状态读不出来 / 数据对不上预期也不按。输入前确认两次：typist 启动时（屏保这类「不是 Winlogon、会话也没锁」的桌面只在这一次放行去唤醒）、唤醒后输入前一刻（**必须读到「已锁定」才输入**）。
3. 日志（`public\helper.log`，用户可读）只记动作和结果码，**永远不记密码**。
4. 只用 **C# 5 语法**：Windows PowerShell 5.1 的 `Add-Type` 自带的是 .NET Framework 4.x 的老编译器。

### 5.4 威胁模型与已知局限

**威胁模型的前提（先读这段）**：这套组件防的是**别的账户**、**低权限沙箱里的进程**，以及**意外**（文件写了一半、被杀软占用、磁盘错误）；**不防登记账户（就是装 Flowship 的那个用户）名下运行的恶意进程**。那样的进程本来就能记录键盘输入、读 Flowship 进程内存、读屏幕，管道和目录 ACL 拦不住它：它能连上管道触发解锁（拿不到密码）、覆盖 / 清除保存的密码（**同时清掉冷却**——重新保存 / 清除密码本来就是冷却的正常出口，见第 9 条）、抢先创建同名管道实例冒充服务端（`CreateNewInstance`，见「已知边界」②）、占满管道实例让服务暂时连不上（「已知边界」⑥）。下面「挡得住 / 挡不住」都以这个前提为准；对外文案（含设置页「安装解锁组件」确认框，`HELPER_TEXT.install`）不要写成「同账户下的程序也碰不到它」。

**挡得住的**：别的账户 / 内置组连管道（ACL + 登记 SID）；普通进程换掉磁盘上的脚本或源码文件（哈希校验；脚本文本和 .cs 文本都是「校验过的那份内存」再拿去执行 / 编译，没有校验完被换掉的空档）；提权进程在校验之外的几个用户态输入——模块搜索路径、`COR_*` 类环境变量、`%TEMP%`、系统目录 / Program Files / ProgramData 的来源——也已逐个钉死（纵深防御，**不是**「提权链不可篡改」，见下面「已知边界」）；预先在数据目录里埋链接 / 抢占目录（可信性检查 + 不跟随链接）；连续输错密码这类**意外和误触发**（一次尝试 + 10 分钟持久冷却；状态文件丢了 / 写坏了 / 被占用这些意外不会让冷却失效，见 §5.3「硬规矩」第 1 条）——**冷却不防同账户的恶意进程**：它重新 `set` 一次密码就能清掉冷却（见第 9 条）；用户已经解锁时误输入（桌面检查）；屏幕上是 UAC 之类的安全桌面时往里输密码（会话锁定标志 + 只信正面证据，见 §3 与 §5.3）；密码出现在日志 / 命令行 / 环境变量 / 返回值 / 步骤事件里（单测断言）。

**挡不住 / 没做的**（如实写明，不要在对外文案里夸大）：

1. **PIN / Windows Hello 为默认登录方式的账户**：锁屏界面根本没有密码入口，组件输入的字符进不了密码框 ⇒ `STILL_LOCKED`，并进入 10 分钟冷却。设置页文案已写明。
2. **没有代码签名**：安装时现场编译出的 exe 没有签名，SmartScreen / 杀毒软件可能拦（编译失败 14、selftest 失败 15、启动失败 17 都可能是它）。
3. **睡眠 / 现代待机 / 合盖不支持**：组件假定屏幕前有一个可唤醒的锁屏界面。
4. **一次性 UAC**：安装 / 卸载各要用户点一次系统授权框。
5. **远程桌面**：Flowship 不在控制台会话里时返回 `NOT_CONSOLE_CLIENT`（只能解锁本机屏幕前的锁屏界面）。
6. **check-then-type 竞态**：输入前确认过两次，输入过程中不逐键复查。每个字符约 50ms（按下 / 抬起各隔 `KeyGapMs/2`，字符之间再隔 `KeyGapMs=25`，带 Shift 的略长），常见 8–20 位的密码要 0.4–1 秒，更长的按长度线性增加。若在这段时间里用户恰好自己解开了电脑，**已经敲出去的字符**理论上会落进用户当前的窗口——上界是整个密码（`Const.MaxPasswordLength`，最多 127 个字符；用户一开始输入就自己解开电脑的话，后面的字符会一直打进他的窗口），不是「几个」（第五轮评审更正）。常见长度的窗口就是 0.4–1 秒，没有做逐键复查。**回车之前**会再确认一次仍是锁屏（输入桌面不是 Default、会话仍是「已锁定」、读不出来也算不行）：不是就不按回车，并按「输过」收场（进冷却）。所以最坏是已经敲出去的字符（上界 127 个）落进用户的窗口，不会替用户提交。
7. **Caps Lock 开着的情况没验证**：组件先 `GetKeyState(VK_CAPITAL)` 读状态、开着就按一下关掉再输；但 typist 线程没有消息循环，读到的状态可能是旧的 ⇒ 大小写反了 ⇒ `STILL_LOCKED` + 冷却。**真机必测**（清单里有）。
8. **遮罩（Windows 上没验证过）**：遮罩靠 `setIgnoreMouseEvents`（鼠标穿透）和 `setContentProtection`（Windows 上是 `WDA_EXCLUDEFROMCAPTURE`，防截屏）。这两项叠加在个别 Win10 / Win11 版本上可能出现穿透失效或遮罩被截进画面，先当作风险来验。遮罩被截进画面时 `capture-guard` 会撤遮罩重截，AI 不会只看到一片遮罩；但**穿透失效**会让 AI 的点击落在遮罩上，表现为「点什么都没反应」。真机必看。
9. **同账户的恶意进程**不在防护范围（前提见本节开头）：它能通过管道触发解锁（拿不到密码），也能覆盖 / 清除密码——而**重新保存 / 清除密码会同时清掉冷却**（用户换了密码，旧的失败记录就不再适用，这是冷却唯一的人工出口），所以冷却对它不构成限制：用一个错误密码 `set` 一次、再 `unlock` 一次，可以反复来，有可能把账户输到锁定（取决于系统的账户锁定策略）；管道上它还能抢先创建同名实例冒充服务端（见下面「已知边界」②的 `CreateNewInstance`），也能占满管道实例让服务暂时连不上（「已知边界」⑥）。这些都不是新发现的洞，是同一个前提的几个后果；真要防只能靠系统层面的隔离（比如把 Flowship 本身跑在另一个账户 / 容器里），不在这个组件的能力范围内。
10. **能改写整个 Flowship 安装目录的恶意程序**连 `protocol.mjs` 里的期望哈希一起改，哈希校验挡不住（它只挡损坏 / 被换掉单个文件 / 意外混入）。
11. 密码字符限制：锁屏界面只认真实键码，目前只支持**英文字母、数字和常见符号**（美式键盘），中文 / emoji / 少见符号保存时就拒绝。
12. 管理员 / SYSTEM 级别的攻击者不在防护范围（见上，DPAPI LocalMachine）。
13. **UAC 判断的边角**：① 判断依赖 `WTSSessionInfoEx` 的结构布局和标志语义（`SessionFlags`：0 = 已锁定，1 = 未锁定，其它 = 未知；Windows 7 上含义相反，不在支持范围内），**没在真实 Windows 上验证过**；代码用「`Level` 必须是 1」「结构里的会话号必须等于本进程会话号」两道对账防偏移猜错，但防不了「标志语义猜错」。② 失败的方向是安全的：读不出来 / 对不上 ⇒ typist 不输入 ⇒ 锁屏自动解锁整个不可用（selftest 在安装时就会因读成「未知」而失败，退出码 27 → 安装失败码 15）；锁屏后台档不受影响。③ 残留的窄竞态：输入前两次确认都是锁屏，但输入的这段时间（密码长度 × 约 50ms，常见长度 0.4–1 秒，见第 6 条）里 UAC 恰好弹出，已经敲出去的字符会落进去；和第 6 条同一性质，没有逐键复查。真正危险的是回车（默认落在「是」上）：它前面有一次紧贴着的复查，会话不是「已锁定」（UAC 就是这种情况）就不按回车，所以只是已经敲出去的字符（上界 127 个）落进 UAC 窗口，不会替用户点同意。④ 驱动一侧在输入桌面读取被拒时同样用会话锁定标志区分；该标志读不出来时驱动按「锁屏」处理（保持旧行为，不让锁屏后台档在 Windows 上整个失效），**把关靠的是 typist 的 fail-closed**，而不是驱动。
14. **管道的 ACE 带 `CreateNewInstance`**（见下面「已知边界」②：冒充服务端；⑥：占满实例）；**提权链的加固是纵深防御**（同上）。

#### 已知边界（审阅后补，如实记录；对外文案不要说得比这更满）

**① 提权链的加固是纵深防御，不是「不可篡改」。**哈希校验只覆盖「脚本文本」和「.cs 文本」。提权进程还会读这些**用户态可以预先布置**的输入，下面是逐个钉死的办法和剩下的缝：

| 输入 | 威胁 | 现在的做法 |
|---|---|---|

仍然**没有**防住的：① 能改写整个 Flowship 安装目录的恶意程序（连 `protocol.mjs` 里的期望哈希一起改，见上第 10 条）；② 同账户进程在 UAC 弹出前的其它布置我们没枚举到的（这份清单是「想到的」，不是「穷尽的」）；③ 下面这些**没在真 Windows 上验证**的假设：`Add-Type` 在 Windows PowerShell 5.1 里确实用 `$env:TEMP` / `$env:TMP`（如果它走的是 .NET 缓存的临时目录，这一条就没起作用，但也没有副作用）；环境变量经 `Start-Process -Verb RunAs` 确实被提权进程继承（如果不继承，清环境变量这一步只是多余）；引导里钉死 `PSModulePath` 后 `Get-Acl` / `Get-ScheduledTask` / `Register-ScheduledTask` 都还能正常自动加载（macOS 上的 PowerShell 7 验证了「钉了之后系统自带模块可用」，但不是 Windows PowerShell 5.1）。

**② 管道上的 `CreateNewInstance`。**组件管道的 ACE 给登记账户的是 `ReadWrite | CreateNewInstance | Synchronize`。`CreateNewInstance` 和「追加写入」（`FILE_APPEND_DATA`）是**同一个比特 `0x4`**，而 Node 侧打开管道用的 `GENERIC_WRITE` 会申请它，不给就会被拒绝或被降级成只读句柄。副作用是：登记账户下的任何进程也能抢先创建**同名**管道实例（名字是随机的，但 `public\pipe.txt` 对普通用户可读）。抢到之后它可以冒充服务端，截获 Flowship 发来的「保存开机密码」请求（`set` 请求里带着密码）。**已接受这个风险**：同一账户下的恶意软件本来就能记录键盘输入、读 Flowship 进程内存、读屏幕，管道防不住它们；管道真正防的是**别的账户**和**低权限沙箱**里的进程（它们连不上，也创建不了）。所以这里的威胁模型是「ACL 防的是账户之间，不防同一账户内的恶意软件」，C# 源码里 `Pipe` 的 ACL 注释写着同样的话（有单测对账：ACE 恰好两条、没有给 `Everyone` / `Users` / `Authenticated Users` 的 ACE、注释里的威胁模型存在）。

**③ 冷却状态的 fail-closed**：见 §5.3「硬规矩」第 1 条。同一账户**之外**的人改不了状态文件（目录只有 SYSTEM / 管理员可写），所以它防的是意外（文件写了一半、被杀软占用、磁盘错误），不是对手；管理员 / SYSTEM 级别的攻击者直接读 `cred.bin` 就够了，不在防护范围。

**④ UAC 之外的「不是锁屏也不是用户桌面」的场景**：`Ctrl+Alt+Del` 界面之类同样在 Winlogon 上的安全界面，按同一原理走和 UAC 相同的判断（会话没锁定 + 输入桌面是 Winlogon ⇒ `SECURE_DESKTOP`），没有单独区分，也**没有**单独验证过。会话锁定标志读不出来时，驱动一侧保持旧行为（按「锁屏」处理，不让锁屏后台档整个失效），把关交给 typist（fail-closed，见第 13 条 ④）。

**⑤ 群里「同权」的非属主轮：`desktop_*` 的拒绝只守 Flowship 自己的工具这一个入口。**Cursor 后端 agent 自带的 shell / 读写文件不经 `invokeFlowshipTool`（SDK 的 `tools` / `disallowedTools` 是 create / resume 级，不能按轮改，而会话是属主轮与群成员轮交替复用的）；macOS 上那个 shell 继承 Flowship 的屏幕录制 / 辅助功能授权（系统按「负责进程」归属授权，**这是推断，没有实测**），`screencapture` / `osascript` 理论上能绕开 `desktop_*`。能做的只有提示词里的叮嘱（同权声明 / 拒绝文案里都写了「别用命令行绕开」），那是软约束；对用户 / 群成员的话术里不要承诺「群成员绝对动不了你的电脑」。同权轮里代码恒拒的清单见 §3 与 `flowship-tools.ts` 的 `GROUP_OPEN_TURN_DENIED_RULES`（11 项：`set_owner_note`、`schedule`(create)、`advance_next`、`create_custom_action`、`browser_storage`、`browser_evaluate`，以及 `browser_network` / `browser_debug` / `browser_perf` / `browser_network_rules` / `browser_permissions` 的特定入参），`desktop_*` 另有专用文案。

**本机 HTTP API 也没有调用者身份**（单机桌面工具的既有模型，`src/lib/local-request.ts` 只校验 loopback / Origin）：同权轮里 agent 的 shell 能直接 `curl` 它——`POST /api/tasks/:id/context-docs` 写任务上下文文档（含标题「所有者备注」，效果等同 `set_owner_note`）、`POST /api/tasks/:id/advance` 推进、`PUT /api/settings` 改设置（含电脑操作的开关）、`GET /api/settings/full` 读 `config.json` 全文。**决定不为它加「渲染进程独有令牌」**：agent 的 shell 与 Flowship 是同一个系统账户，数据目录里的 `config.json` / 任务文件它本来就读写得到，令牌挡不住，只会制造「已隔离」的错觉。所以恒拒清单的准确定位是**正常工具路径上的第一道闸**（防模型被群成员一句话带偏、顺手调这些工具；防提示注入），**不是对一个有意绕行的 agent 的隔离**；要隔离只能是「Cursor 后端按轮次收窄 shell」这类结构性改动，目前做不到。同样的话不要写进对用户 / 群成员的承诺里。

**⑥ 同账户进程占满管道实例：只影响可用性，会自动恢复。**管道 ACE 给登记账户 `CreateNewInstance`（②），而管道最多 8 个实例（`MaxInstances=8`）、每个连接 90 秒后被服务端关掉：登记账户下的进程可以连着不说话把实例占满，让 Flowship 暂时连不上组件（解锁请求失败）。失败怎么记账：解锁器只把「连管道就失败」的两种（`NOT_RUNNING` / `DENIED`）算作没输过密码、不进冷却，**其它（超时 / 通信出错：`TIMEOUT` / `IO`）一律按「试过一次」算、会进 10 分钟冷却**——实例被占满时 Node 侧具体落在哪一种取决于 Windows / libuv 对「管道忙」的处理，**没验证**。这是宁严勿松的方向（不会多输密码），代价是占用期间还会顺带吃一段冷却。**服务本身不会因此退出**——以前「连续失败 20 次就退出 + 计划任务只重启 5 次」会把这种占用变成永久停摆，现在运行阶段接不到客户端 / 建不出新实例一律只做「丢掉坏实例、退避重试、限频记日志」（§5.3），占用一消失就自己恢复。占着实例不放的进程**读不到密码、也解不了锁**；真正能截获密码的是抢占同名实例冒充服务端（②）。两者同属「同账户恶意软件不在防护范围」（本节开头）。**这个行为只做了静态对账 + C# 5 编译检查，没在真实 Windows 上验证过**（验证步骤见 `docs/windows-unlock-live-test.md`）。

## 6. 怎么改、怎么验证

**改资源文件**：见 §5.3「铁律」。改协议（动词 / 结果码 / 常量 / 键位表 / 退出码）要 C# 与 `protocol.mjs` 同时改，`tests/desktop-win-helper-protocol.test.ts` 会静态对账（两边的常量、键位表、动词、结果码双向、退出码双向、哈希、C# 5 禁用语法、`Log.Write` 里不出现密码标识符）。组件有不兼容变化时，C# 的 `Const.Version` 与 `protocol.mjs` 的 `HELPER_VERSION` 同时 +1（**不只是协议变化：改的是 service / typist 的运行行为也要升**——第三轮的冷却恢复语义就是漏了这一步，第四轮评审 P1-2 才补成 v2；第五轮 `DoSet` 的行为又变了（冷却记录早已过期时不再误报 `COOLDOWN_NOT_CLEARED`），升到 v3；第六轮评审 P2-3 里 `CredStore` 判断开机密码「有没有」的方式变了（不再用 `File.Exists`），升到 v4；对账测试只比两边一致，不会替你判断该不该升），设置页会提示「已装的解锁组件是 vX，和这版 Flowship 要的 vY 不一致。点「安装」升级一次」。
